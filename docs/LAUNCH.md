## 发布前

1. 用自己准备发布的 GitHub 账户创建公开仓库，确认仓库名与许可证；账户和仓库归属由发布者选择。
2. 检查 [README](../README.md) 首屏、[封面](../assets/hero.png)、两份示例与[方法说明](../skills/ai-job-countdown/references/methodology.md)的链接和显示效果。封面 PNG 为 1280×640，可用于 GitHub Social preview；需改文字时编辑同目录 SVG 再导出。
3. 在计划支持的 Agent 中实际运行 README 的安装命令，完成一轮真实任务访谈；记录宿主、模型、日期和问题。只声明已经验证的兼容范围。
4. 检查报告是否区分任务接管与岗位编制；时间窗是否围绕同一事件、有起算日期和前提信号；信息不足是否写明无法估计；行动是否可以验收。
5. 检查所有公开文件与截图，移除身份信息、客户名称、内部资料和密钥。演示案例保留“演示”标识。
6. 推送仓库后再核对在线 README；如发布首个版本，可用 `v0.1.0` 并说明当前交付范围、已验证环境和局限。

公开仓库：[Singapo/ai-job-countdown](https://github.com/Singapo/ai-job-countdown)。远程安装命令如下，宿主安装效果仍需实测：

```bash
npx skills add Singapo/ai-job-countdown --skill ai-job-countdown
```

## 可直接改写的发布文案

发布文案：

```text
你的工作，距离 AI 接管还有多久？

我做了一个开源 Agent Skill：AI Job Countdown / 工作倒计时。
聊聊你最近一周具体做了什么，它会分析哪些任务能与 AI 协作、
哪些有条件代办、哪些已经有代办证据，哪些还需要人来主导。

报告包括有前提的情景时间窗、会改变判断的信号，
以及一份有验收标准的 30 天行动。信息不足时，会写明无法估计。

仓库里放了两份产品经理案例：一个偏交付，一个偏探索。
希望它帮你找出下一步值得验证的变化。

欢迎试用，也欢迎用匿名案例和反例挑战它。
https://github.com/Singapo/ai-job-countdown
```

适合演示的素材：README 封面、两份案例中的同类任务对照，以及一张匿名 Markdown 分享卡。展示截图时同时保留报告日期、演示标识和关键前提，避免把条件情景裁剪成确定性倒计时。

## 邀请匿名案例贡献

可以在 Issue 中使用下面的模板；没有真实观察的项目写“未知”即可：

```text
职位 / 行业（可粗略描述）：
主要任务、时间占比与交付物：
谁负责验收，验收标准是什么：
公司采用 AI 的条件或限制：
试过的 AI 流程与实际观察：
报告日期、Agent 与模型：
哪条结论需要修正，为什么：
```

投稿前移除姓名、公司、客户、文档原文等可识别或非公开信息。维护者如要把投稿改成仓库案例，先征得投稿者对公开内容的同意，并标注证据来自自述还是可核验记录。

优先处理三类反馈：同一任务的反例、判断前提缺失、30 天行动无法验收。用这些反馈改进 Skill 与现有示例；有实质更新时发布简短变更说明。Star 可作为关注度信号，不能验证预测是否准确。
